1. 먼저 읽기 — Pass / Fail / Skip과 Run All

정적 분석 도구 자체를 처음 볼 때 · 아래 Q&A를 위에서부터 읽으면 됨

애초에 이걸 왜 만들었나?

의도: Play로 87개 QA를 매번 돌리기 전에, “AI·코드 수정이 내 합의(의도)대로 반영됐는지”를 빠르게 확인하고 싶다.

예: 1차 구간 -403 해제됐는지, 고속 접촉이 FixedUpdate로 고쳐졌는지, 오염원 제거 후 아이템 선택이 유지되는지 — README·AGENTS·회의록에 적힌 계약이 코드·씬·JSON에 그대로 있는지 Play 없이 검사한다. 체감·연출·BGM은 여전히 Play로 본다.

Run All은 뭐야? 터미널 명령? Play?

의도: Unity 안에서 클릭 한 번으로 전 규칙을 돌리고, 결과를 HTML로 받고 싶다.

Unity 에디터 상단 메뉴 MidProject > Static Analysis > Run All 이다. 터미널 명령도, 게임 Play도 아니다. static_rules.json 22규칙(F01~F22)을 한 번에 검사하고 static-analysis-report.html을 만든다. Console에 Pass N, Fail N, Skip N 요약이 뜬다.

Pass / Fail / Skip은 각각 뭐야?

의도: 리포트 한 줄만 봐도 “의도대로인지 / 깨졌는지 / 이번엔 검사 안 함”을 구분하고 싶다.

Pass — 의도·규칙대로 코드·파일·값이 맞음. 예: Pollutant.cs에 OnTriggerStay2D + ApplyPlayerContactDamage 있음.
Fail — 규칙 위반. 예: Pollutant.cs에 ResetToDefault 재등장, GameScene moveSpeed가 400이 아님.
Skip — 이번 실행에서 조건 미충족으로 검사 생략(실패 아님). 주로 F19·F20: GameScene을 에디터에 안 연 상태면 Skip. “Skip 많다” ≈ GameScene 안 연 채로 Run All 돌린 것.

GameScene을 꼭 열고 Run All 해야 해?

의도: 코드 기본값 말고, 실제 씬에 박힌 숫자·Inspector 연결까지 의도 검증에 넣고 싶다.

권장: Unity에서 GameScene.unity 연 뒤 Run All. F19(Manager 참조 null), F20(moveSpeed 400 / scrollSpeed 0.2)이 그때 Pass/Fail로 나온다. 안 열면 F19·F20만 Skip이고 나머지 F01~F18, F21~F22는 그대로 검사된다.

project-static-analysis.html 이랑 static-analysis-report.html 차이는?

의도: “규칙 설명서”와 “오늘 돌린 결과”를 파일로 나누고 싶다.

project-static-analysis.html (이 문서) — 스펙·의도·Q&A 설명서. Run All 전에 읽는 용도.
static-analysis-report.html — Run All 실행할 때마다 자동 생성되는 결과표. Pass/Fail/Skip + 메시지.
메뉴: Open Spec (HTML) → 이 문서 · Open Latest Report → 마지막 결과.

실제로 뭘 하면 돼? (한 줄 흐름)

의도: 매번 수정 후 “의도 깨졌나?”만 1분 안에 확인하고, 체감은 Play로 짧게 본다.

1) Unity 열기 → GameScene 열기
2) MidProject > Static Analysis > Run All
3) 리포트에서 Fail 0인지 확인 (Fail 있으면 메시지 보고 수정)
4) 필요하면 Play로 접촉·속도 체감만 짧게 확인
의도 반영 = Run All · 느낌·연출 = Play

4. 기능별 Q&A — 의도와 설명

각 Q = 그 기능에 대한 합의·의도 · A = 왜 그렇게 구현·검사하는지 · Run All의 Pass/Fail과 연결

F01. 씬 흐름

의도: 게임은 항상 Splash → Title → Intro → Loading → Game 순으로만 들어가야 한다. Build Settings 순서가 바뀌면 안 된다.

5단계 파이프라인(스플래시 → 타이틀 → 스토리 → 로딩 → 본편)이 Build Settings에 정해진 순서로 등록돼 있는지 검사한다. 코드가 맞아도 Build 순서가 틀리면 빌드·첫 실행부터 꼬이므로, 게임의 “문”이 어디서 어디로 열리는지를 가장 먼저 고정하는 규칙이다.

F02. 스테이지 데이터

의도: 맵마다 어떤 오염원이 나올지는 코드에 박지 말고 JSON으로 두고, mapPollutants로 구간별 스폰을 관리한다.

stage_data.json에 mapPollutants가 있어야 PollutantManager가 맵 구간별 오염원 계획을 읽을 수 있다. 기획·밸런스를 스크립트 수정 없이 JSON에서 바꾸는 구조이며, 런타임에는 PollutantSpawnPlan이 이를 소비한다.

F03. 회복 아이템 데이터

의도: 회복 아이템 종류·이름·효과도 코드 하드코딩이 아니라 recovery_items.json 한곳에서 관리한다.

회복 인벤은 JSON → RecoveryItemInventory 로드 → UI·픽업이 쓰는 흐름이다. 중화 아이템(Item)과 분리된 데이터 소스로 회복 종류를 관리한다. 항목 밸런스는 Play·기획 영역이고, 데이터 파일 자체가 사라지지 않았는지가 1차 방어선이다.

F04. 플레이어 이동 (물리 동기)

의도: 이동은 Update에서 Transform만 밀지 말고, FixedUpdate에서 Rigidbody2D.MovePosition으로 물리와 맞춰야 접촉이 안 끊긴다.

고속 이동 시 Update + MovePosition이 트리거를 건너뛰는 것이 접촉 끊김의 핵심 원인이었다. moveInput은 Update에서 받고, 실제 위치 변경은 FixedUpdate의 rb.MovePosition으로 나눴다. 누가 다시 “Update에서만 이동”으로 되돌리면 Fail — 속도를 올려도 접촉이 유지된다는 의도의 기반이다.

F05. 1차 이동 구간 기본값

의도: 시작 구간은 왼쪽 -785, 오른쪽 -403까지. 맵 전환 끝 지점은 769. 이 숫자가 Player 기본값으로 유지돼야 한다.

가이드 끝 후 처음 걷는 1차 구간이 -785 ~ -403이고, 오염원 클리어 후 넓어지는 끝이 mapAdvanceRightX = 769이다. GameScene에서 숫자를 덮어쓸 수 있지만, 코드 기본 계약이 바뀌면 맵 설계 전체가 어긋날 수 있어 스크립트 쪽도 고정한다.

F06. 1차 구간 해제

의도: 첫 오염원이 활성화되면 -403 한계가 풀려서 mapEnd(769)까지 갈 수 있어야 한다. 그 로직이 PollutantManager에 있어야 한다.

-403에 갇힘 버그 대응으로 TryUnlockSegmentMovement() → UnlockMapSegmentMovement() 흐름을 넣었다. 경고·스폰 직후, 이미 오염원이 있는 경우, A~C 클리어 후 다음 구간 등 “이제 이 맵 플레이 시작” 타이밍에 호출된다.

F07. 오염원 접촉 (A~C / D 동일 경로)

의도: A, B, C, D 모두 OnTriggerStay에서만 데미지. IsEdgeContact로 접촉을 다시 조이면 안 된다.

회의록 §4 합의: 접촉·데미지 경로는 A~C와 D가 같고, D만 밸브 연출이 추가된다. OnTriggerStay2D → ApplyPlayerContactDamage가 표준이다. IsEdgeContact는 예전 “가장자리만 닿을 때” 조건으로 접촉 중 데미지 끊김 원인이 됐고, 지금은 정의만 남고 호출은 금지한다.

F08. 접촉 보정 (고속 이동)

의도: FixedUpdate만으로도 트리거를 놓칠 수 있으니, Pollutant가 LateUpdate에서 bounds 겹침으로 접촉을 보완해야 한다.

LateUpdate에서 IsBoundsOverlappingPlayer, GetContactOverlapPadding으로 겹침 fallback을 둔다. 속도 400에서도 HP바·데미지·판정이 끊기지 않게 하는 이중 안전망이다.

F09. BlockPollutant 금지

의도: 예전처럼 BlockPollutant로 플레이어 이동을 인위적으로 막는 방식은 다시 쓰지 않는다.

지금은 leftLimit/rightLimit·구간 해제·가이드 canMove로 이동을 제어한다. Assets/Scripts 전체에서 BlockPollutant 문자열이 한 줄이라도 있으면 Fail — 회귀 방지용 빨간 줄이다.

F10. 중화 아이템 선택 유지

의도: 오염원 HP가 0이 돼도 Pollutant 경로에서 ResetToDefault()를 호출하지 않는다. Z/X로 고른 아이템은 맵 진행 내내 유지.

합의: 첫 경고만 기본 중화, 이후 선택 유지, 스테이지 리셋 때만 Scanner 초기화. Pollutant.cs에 ResetToDefault가 없어야 Pass — HP 0 처리에서 리셋이 재도입됐는지 잡는다.

F11. 클리어·사망 연출 타이밍

의도: 클리어/다이 애니가 먼저, 결과 패널은 기본 2초 뒤. 애니와 패널이 동시에 뜨면 안 된다.

clearAnimDelay = 2f, dieAnimDelay = 2f 후 Clear/GameOver 패널. 클리어 시 player.FreezeClearAnim()으로 애니 상태 고정. 연출 → 잠깐 여운 → 결과 UI 순서를 지킨다.

F12. 경고 구간 입력 차단

의도: 오염원 경고·스폰 연출 중에는 IsWarningFreeze로 Z/X 아이템 선택 같은 입력을 막아야 한다.

경고 텍스트·페이드·스폰 동안 아이템을 바꾸면 판정·UI가 꼬일 수 있다. ItemSelectManager가 IsWarningFreeze를 보고 입력을 막는 구조다.

F13. 맵 구간 전환

의도: A~C 오염원을 없앤 뒤 pendingMapAdvance로 mapEndX(769)까지 가면 다음 맵·다음 오염원으로 넘어간다.

한 맵에서 ABC 클리어 → 플레이어가 mapEndX까지 이동 → MapAdvanceRoutine으로 배경·구간·다음 스폰. pendingMapAdvance는 “지금 맵 끝까지 가야 한다”는 플래그다.

F14. 회복 인벤 (스크립트 3종)

의도: 회복은 데이터(JSON) + 인벤 로직 + UI + 맵 픽업 스크립트가 세트로 있어야 한다.

RecoveryItemInventory.cs(스택·선택·사용), RecoveryItemInventoryUI.cs(InvItemView, dim, Count), RecoveryItem.cs(맵 픽업). 중화 HUD와 분리된 회복 인벤 파이프라인이다. UI 레이아웃·스크롤 품질은 Play로 확인한다.

F15. Item.ItemType 타입 규칙

의도: 전역 enum ItemType을 새로 만들지 말고, Item.ItemType만 쓴다.

다시 enum ItemType을 Scripts에 넣으면 타입 충돌·판정 버그가 난다. 네이밍·타입 계약을 고정하는 규칙이다.

F16. 접촉 해제 시 오염원 HP 초기화

의도: 플레이어가 오염원에서 떨어지면 pollutanCurHp는 pollutanMaxHp로 돌아간다. 가스(D)도 예외 없음.

EndPlayerContact에서 pollutanCurHp = pollutanMaxHp. 잠깐 닿았다 떨어지면 오염원 HP 진행이 리셋되는 것이 의도된 난이도·리듬이다.

F17. 중화 VFX

의도: RefreshNeutralizationVfx는 맞는 A~C 아이템(IsSelectedItemRecommendedFor)일 때만 켠다. 틀린 도구·스캐너·가스(D)는 VFX 없음.

“스캐너가 아니면 VFX ON”처럼 단순화하면 틀린 도구에도 이펙트가 다시 나온다. D(가스)는 밸브 애니·SFX만 — 정답 A~C만 VFX라는 의도의 코드 앵커다.

F18. 오염원 스폰 플랜·프리로드

의도: 오염원은 맵 계획(PollutantSpawnPlan)대로 미리 BuildPreloadedPollutants 하고, 때가 되면 TryRevealPreloaded로 공개한다.

경고 전 프리로드 → 경고·페이드 후 reveal. 스폰 타이밍·맵 진행과 데이터 계획이 분리되게 한다.

F19. GameScene Inspector 참조 (씬 열림 시)

의도: GameScene에서 GameManager·PollutantManager의 player, spawner, timer 등 핵심 참조가 null이면 안 된다. Player에는 Rigidbody2D가 있어야 한다.

코드 패턴만 맞아도 Inspector 미연결 시 Play에서 NullReference. GameScene이 에디터에 열려 있을 때만 검사하며, 씬 안 열면 Skip(Fail 아님).

F20. GameScene 속도 기대값 (씬 열림 시)

의도: 실제 플레이에 적용되는 moveSpeed는 400, Background scrollSpeed는 0.2(실플레이 체감 확정)여야 한다.

배경은 오프셋 스크롤(SetTextureOffset) — 패럴랙스 아님. 런타임에 쓰이는 건 씬에 박힌 값. 1:1 참고: scrollSpeed ≈ moveSpeed / 1920 (400 → ≈0.208). 실플레이 확정 0.2. F20은 400/0.2 쌍이 씬에 있는지 본다.

F21. 핵심 스크립트 존재

의도: README·AGENTS에 적힌 핵심 파일 7개가 프로젝트에 있어야 한다.

Pollutant, Player, GameManager, ItemSelectManager, PollutantSpawnPlan, Background, GuideTxt — 게임플레이 최소 뼈대가 파일 단위로 intact한지 보는 규칙이다.

F22. 회복 맵 드랍·클리어 자동 수집

의도: 맵에 떨어진 회복 아이템은 landedMapItemCount로 추적하고, 스테이지 클리어 시 AutoCollectMapRecoveryItems로 남은 것을 자동 획득한다.

RecoveryItemManager가 맵에 남은 개수를 세고, 클리어 시 GameManager 경로로 일괄 수집한다. 드랍·클리어 수집 기능이 통째로 빠지지 않았는지 확인한다.

Run All과 이 Q&A의 관계

의도: 기능마다 의도가 문서·코드에 맞는지, Play 전에 한 번에 확인하고 싶다.

Unity에서 GameScene 연 상태로 MidProject > Static Analysis > Run All → static-analysis-report.html에서 F01~F22 Pass/Fail/Skip 확인. Q에 적은 의도가 Fail이면 깨진 것, F19·F20 Skip은 GameScene 미로드일 때다.

6. 규칙 추가 방법

  1. Assets/Data/static_rules.json에 rules 항목 추가
