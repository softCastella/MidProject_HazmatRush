## 2. 공통 목차 패턴

```text
표지 → 목차 → 게임 소개 → (레퍼런스) → 개발 과정
  → 시연/영상 → 콘텐츠·시스템 → 문제·해결 → 아쉬운 점·이후 → 감사
```

| 섹션 | 등장 빈도 | 역할 |
|------|-----------|------|
| 게임 소개 | ~100% | 짧게 “무슨 게임인지” |
| 레퍼런스 | ~70% | 기획 근거 |
| 개발 일정·툴 | ~80% | 과정·신뢰 |
| 시연·영상 | ~90% | 플레이로 설득 |
| 핵심 시스템 | 필수 | 구현 증명 |
| 문제·해결 | ~60% (강한 자료) | 개발 역량 |
| 아쉬운 점 + 이후 | ~90% | 마무리 |

**관찰:** 중간 발표(Dream Survivor, 모험의 서)는 **컨셉·로드맵** 비중, 최종은 **시스템·출시·수치** 비중이 크다.

## 3. 중간 vs 최종

| 구분 | 중간 | 최종 |
|------|------|------|
| 분량 | 16~36장 | 27~51장 |
| 비중 | 컨셉·UI·기획 | 시스템·코드·출시 |
| 영상 | 있거나 예정 | 거의 필수, 2~3분도 흔함 |
| 문제·해결 | 1~3건 | 다수 + Before/After |
| 출시 | 예정 | 스토어·QR·날짜 |

## 7. 「문제·해결」 슬라이드 (DeadCity 기준)

```text
현상 → 원인 추정 → 근본 원인 → 해결 → 인사이트
```

**DeadCity 사례 (타 팀):**

- Input Action Manager Scene 중복 → VR 컨트롤러 정지
- 손목 HUD 흔들림 → Curved UI로 전환
- 수류탄 그립 → Velocity Tracking + Throw Scale

## 8. 데모 영상 (타 팀 패턴)

| 패턴 | 예시 |
|------|------|
| 기능별 `[영상]` | Flap of Rage |
| 시연 **시나리오 표** | DeadCity (1P/2P, Zone별) |
| “플레이 영상” 1장 + 본편 | 최종 발표에서 **2~3분** 다수 |

중간 발표(Dream Survivor)는 **UI 목업·시연 영상** 슬라이드가 있으나, 본편 길이는 자료마다 상이.

---

## 9. 타 팀 발표에서 자주 보이는 “성공 공식” (일반화)

> **짧은 컨셉 + (영상) + 구현 3~5개 + 막혔던 것 1~2개 + 앞으로**

- **Merge·Disc型** (레퍼런스만 / 이미지만) → 설득력 낮음
- **펭귄·CGV型** (시스템 10장+) → 분량·발표 시간 많을 때
- **DeadCity型** (Issue 구조화) → 개발 역량 전달에 유리
